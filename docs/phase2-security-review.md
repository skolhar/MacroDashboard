# Phase 2 administrative security review

The API accepts a single SHA-256 digest from `ADMIN_TOKEN_SHA256` and compares it to `X-Admin-Token` with constant-time `hmac.compare_digest`. Production and staging fail startup if the digest is absent or malformed; demo observations are forbidden there. The token is not returned by API handlers or included in the frontend bundle. Administrative writes require the token, and requests are size-limited and validated.

This remains a **shared bearer credential**. It has no operator identity, scoped permissions, expiry, rotation overlap, revocation per user or independent audit attribution. SHA-256 storage does not compensate for a low-entropy token. Before multi-operator production administration, replace it with an identity provider or gateway that issues short-lived identities and scoped roles, logs actor IDs, and supports rotation and revocation. Store secrets outside the repository and frontend build environment.

`RateLimiter` uses process-local monotonic-time buckets. Regression tests verify exhaustion within one instance and independence between instances. Separate API workers or replicas therefore do not share a quota. Behind the current Caddy reverse proxy, the API also sees the proxy peer as `request.client.host`; one public client may consume another's shared bucket. Do not trust `X-Forwarded-For` supplied by arbitrary clients to work around this. A production rollout should enforce quotas at a trusted ingress or shared store with a verified client identity, then load-test across replicas. The in-memory bucket map is also unbounded in distinct keys, so trusted ingress limits should precede public multi-replica use.

The current Caddy route exposes OpenAPI docs. This is not a credential leak by itself, but the deployment owner should decide whether to restrict them. These limitations are review blockers for high-volume public or multi-operator administration; no production configuration was changed in this PR follow-up.

# Governed source-release archive

The existing Phase 3A two-operator review now retains original publisher bytes in a content-addressed volume outside PostgreSQL. The volume is independent of production and mounted only in isolated staging. Configure an absolute `SOURCE_ARCHIVE_ROOT`; absent configuration fails closed. Its `sha256/` files are created with mode 0600 and checked for integrity on every review, approval and import. Back up this volume with the staging database and restrict filesystem access to operators. Restore both together; missing or changed archive bytes block import and review.

1. A scoped importer obtains the original release from an authorised publisher path, checks its actual source URL, saves independently documented publication evidence, and confirms the licence covers storage, processing and the intended public display.
2. Upload unmodified original bytes as `application/octet-stream` to `POST /api/v1/admin/releases/archive` with `X-Source-Provider`. Record the returned `archive://sha256/…` reference and SHA-256. A duplicate upload reuses the object. The 750 KB limit is deliberate; larger releases need a reviewed storage change.
3. Create a reproducible seven-column CSV extract. Submit `/api/v1/admin/releases/reviews` with both hashes, the original archive reference, source and publication-evidence URLs, an evidence note explaining how the **actual** timestamp was established, the entitlement basis and contract reference, and a versioned indicator definition. Do not fill unknown historical timestamps with the current ingestion time or a guessed market close.
4. A different operator with `releases:approve` downloads `/api/v1/admin/releases/reviews/{id}/original`, examines the publisher bytes and external evidence, confirms the entitlement, and records an approval note. Identity, decisions and imports are auditable in the database.
5. Import through `/api/v1/admin/imports/release` with the approved review ID and unchanged original bytes and CSV extract. The importer compares both hashes and archived bytes before ingesting. It preserves source publication time separately from actual ingestion time and links observations to the approved review. Duplicate imports are idempotent; revisions create new vintages. The original archive remains authoritative for later inspection.

The archive is a byte-preservation mechanism, **not a signature verification or licence authority**. A reviewer must establish authenticity, timing and usage rights independently. The archive must never be mounted into the web container or served publicly. Source references shown in the monitor point to publisher URLs, while archive bytes require an administrative approval scope.

For historical backfill, run `python -m scripts.phase3b_gap_report` in isolated staging and keep the JSON alongside the reviewed release inventory. `source_known` reconstructs what a publisher had released by the evaluation timestamp; `system_known` reconstructs what SmartHedge had ingested by then. Neither substitutes for the other. Years without a verified India trading calendar report unknown daily gaps rather than guessed sessions.
